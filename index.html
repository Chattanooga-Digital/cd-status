Recently shipped

The last few weeks, most recent first.

4 Aug

Membership system moved inside the website

Members will sign in once, not twice. Existing contacts and groups carried across, and card payments installed. This had been reported for weeks as blocked by a firewall; it was not. The payment add-on needed a second add-on that happens to be named "firewall", and the error naming it read like a blocked connection. Nothing on the server ever needed opening.

4 Aug

Files uploaded to the membership system were readable by anyone

Attachments could be downloaded by anyone who guessed the address, with no sign-in. The software ships a protection against exactly this, but it only works on a different kind of web server than the one we run, so it was present and doing nothing. Fixed, and confirmed by putting a file there and trying to fetch it before and after.

4 Aug

Scheduled background work had never actually run

The website's routine background tasks were failing silently, which is why the calendar had stopped picking up new events. Fixed on the live site and the test one. Also fixed the reason nobody noticed: the deployment process was reporting failures as successes, so several steps had been quietly failing for weeks while every log said they had worked.

3 Aug

Membership records brought current, and put under version control

Updated three releases, including a security fix that mattered. Its setup now lives in a repository instead of only inside a control panel, which is what makes moving it to production possible at all.

3 Aug

Every service pinned to a known version

Several services were configured in a way that looked like it kept them updated but silently froze them at whatever was current on the day they were created. All are now explicitly pinned, so a version change is a visible, reviewed decision.

1 Aug

File and collaboration service rebuilt on safer foundations

Replaced the packaged version with one assembled from reviewable parts, removing a component that could have reached other tenants on the shared server.

Late Jul

Website moved to the current Drupal release

Along with the members' hub going live and outgoing mail moving to a provider that reliably delivers.

How something gets from idea to live

Worth stating, because it explains why things sit in testing rather than shipping the day they work.

First

Built in code

Configuration lives in a repository, not in a control panel. If it only exists somewhere clicked, it can't be reviewed and can't be rebuilt.

Then

Rebuilt from scratch

Staging is wiped and rebuilt from that code. That's deliberately harsher than copying production, and it catches faults a warm copy never would.

Then

Checked by rendering it

Someone opens the actual pages and uses the actual features. A server replying “fine” is not evidence that anything works.

Finally

Opened to members

Only once it's reviewed. Reversing a service after real member data is in it is far more expensive than waiting a week.

Staging mirrors production's setup, not its contents. A rebuild wipes the database and starts from what's in the repository, so staging is a faithful copy of how things are configured and deliberately not of members' real data. That's what makes it safe to destroy — and it means a test there won't reveal anything that depends on real content.
